## Review

- 目标：把线下《用章（印）申请单》搬进「我的申请」，并跟踪 5 类章的占用状态。
- 关键设计：①「时段占用」与「实体在借」拆成两个正交概念 —— 逾期自动释放占用后，章会显示可用但实体仍在别人手上，靠 `physicalOut` 非阻断提示兜住这个物理矛盾；②冲突判定是区间互斥（`useAt < 对方归还 && 对方用章 < 本申请归还`），无法用唯一索引表达，一期用「提交校验 + 审批通过复检」两道查询覆盖 TOCTOU 窗口，不引入租户级锁；③「审批中」也计入占用，否则会批完才发现撞车；④复用考勤的审批动作与代理审批人（`attendanceRoles.general_manager` / `attendanceGeneralManagerDelegateId`），但审批只有总经理一级，且独立建模，不被考勤开关与台账耦合。
- 字段上补了图上没有但必需的 `actualReturnAt`（问题 2、3 的判据来源）、`checkedOutAt`、`forcedReturn` 留痕。
- 补充需求（同日）：**印章保管员**（可按章类别分别指派，未指定回落到统一保管员）+ **章使用台账**（`SealUsageLog`，只追加不修改）。落到设计上：申请人不再填「经办人」（由保管员发章时写入）；发章 / 收章 / 催还 / 强制归还**只有保管员能操作**，接口层校验，杜绝「没记录就算用了」；每次动作都写一条台账，可按章 / 时间 / 动作查、可出每枚章的使用次数与逾期统计。未配保管员时禁止启用模块。
- 补充需求（2026-09-28，三条，其中两条推翻前议）：
  1. **设专职保管员，权限由管理员设置** —— 「管理员」在本仓 = `privilege` 含 `admin`，与 owner 不是一个东西；App 此前只有 `requireExactOwner`（`controllers/api/attendance.js:158`，只认 `role==='owner'`），已有 `requirePeopleManager`（`:163`）是 owner-or-admin 范式 → 保管员指派判据改照它写，**不再用 `requireExactOwner`**。主用法是**一名专职保管员**，按类别分别指派降为可选项（`sealCustodians.byType` 覆盖 `default`）。
  2. **审批权限就是总经理，一次审核即可**（推翻此前「部门主管 → 总经理」两级，且**不留配置项**）→ `sealApprovalMode` 这个枚举直接**取消**，审批链固定单级：取 `attendanceRoles` 含 `general_manager`（复用 `attendanceGeneralManagerDelegateId` 代理审批人），**不取 `managerId`**；申请表上「部门主管意见」一栏随线下流程一起取消。注意区分：§5.3 催办链里仍会通知部门主管，那用的是 `user.managerId`，是**上报对象**、不是审批人，别把两处混起来。上一版我还想留个 `manager_then_gm` 开关，用户明确否掉了 —— 「一般」二字不足以支撑加配置，能少一个枚举就少一个。
  3. **每个类别可有多枚章，枚数由保管员设置，启用时预置每类 1 枚**（推翻此前「每类仅一枚」）→ 这是最贵的一条：新增实体章模型 `SealItem`，**「枚数」不再是一个数字字段，而是该类 `status='active'` 的 `SealItem` 条数**（避免「改了数字但发不出章」的不一致）；首次打开开关时**幂等预置 5 个类别各 1 枚**（`公章-1` / `财务专用章-1` / …），开箱即用，保管员再按实有数量增删；占用判定从「类别唯一锁」升级为**容量判定**（区间内独占并发数峰值 `< 在用枚数`），**必须用扫描线求峰值并发**——简单数「重叠条数」会在两条申请各自与目标区间相交但彼此不相交时误判成 2 个占用；发章时保管员指定具体某一枚并写 `sealItemId`，台账因此可追溯到「哪个章被谁借走」（这才是用户要的「记录每个章的使用情况」）。物理矛盾（`physicalOut`）从类别级收窄到**逐枚**，逾期释放的是**名额**、不是实体。

# 后端 dev 脚本开启自动重启（2026-09-26）

- [x] 查明 `pnpm run dev` 其实就是 `node app.js`，没有任何监听
- [x] 把 dev 改成 `node --watch app.js`（Node 22 自带，零依赖），start / dev:saas 不动
- [x] 验证脚本解析、`--watch` 重载行为，并更新长期笔记

## Review

- 原因：`package.json` 里 `dev` 与 `start` 一样都是 `node app.js`，pnpm 只是脚本运行器不会加监听；Node 把 `require()` 的模块缓存在内存里，磁盘改了进程也不会重读，所以必须重启。
- 改动：`"dev": "node --watch app.js"`（`start`、`dev:saas` 保持裸 `node app.js`，部署侧行为不变）。`pnpm run` 已能列出新命令。
- 边界：`--watch` 是整进程重启（在途请求会断、启动瞬间端口不可用、内存态重置），只监听进程 require 过的模块，`.env`/`views/*.pug`/`public/`/`data/`/`uploads/` 不在监听范围；pug 模板开发态每次请求重读，本来就不用重启。
- 验证：临时脚本实测改被 require 的 .js 后自动打印 `Restarting ...` 并加载新版本；`node -e` 校验 package.json 解析正常；已同步更新 `.workbuddy/memory/MEMORY.md` 里的启动方式说明。
