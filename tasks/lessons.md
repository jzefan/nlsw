# Lessons

- 当需求描述是“默认是物流公司的”“保存后下次打开还是修改后的”这类全局业务配置时，先优先按“租户级/公司级共享配置”理解，不要先假设成“当前登录用户专属”。
- 还要继续区分“公司级通用设置”和“某个业务功能内的共享配置”：如果用户说明“每个用户都能改，但别人也能看到”，应优先建模为该功能的共享业务配置，而不是用户偏好。
- 对已有报表页面加小功能时，优先沿用原有版式，只做最小侵入交互；像“抬头可修改”这类需求，先考虑“文字后小图标 + 弹窗编辑”，不要默认新增整块编辑区。
- 做搜索结果或选择列表时，如果用户明确要“像表格一样一行一条”，不要先用卡片式上下两行排版；应优先用带表头的行式布局，再根据空间做截断。
- 做弹窗搜索或空状态时，不要只放一行功能说明文字；优先提供更完整的居中空状态，引导用户知道能搜什么、系统会怎么返回结果，同时先检查弹窗宽度是否足够承载内容。
- 做远程搜索输入框时，不要只满足“能搜”；默认就要加足够明确的防抖，并处理旧请求结果覆盖新输入的问题，避免用户快速输入时产生多次无效请求或结果闪动。
- 做搜索结果表格时，字段以用户明确列出的业务字段为准，不要只展示“够用”的简化列；后端返回结构要一次把这些字段补齐，前端只做排版和格式化。
- 调整弹窗尺寸时不要一把拉到很宽；如果用户只说“再宽一点”，应优先做中等幅度调整，并结合当前场景控制在合理阅读宽度内，而不是直接上超宽桌面尺寸。
- 在固定宽度弹窗里做结果表时，列宽不要继续写死像素；优先用 `fr` 比例列让字段跟随弹窗整体宽度自适应，再配合截断控制信息密度。
- 搜索结果表里不要默认所有字段都 `truncate`；应按字段重要性区分，像提单号、订单号这类关键标识要完整显示，其他说明性字段再允许换行或截断。
- 车船结算页的列表、统计和导出都会各自重建主行与内部运单行；修改状态筛选时必须逐一核对，船主状态不匹配不等于内部运单也应被排除。
- 做搜索结果跳转时，不要让前端再根据展示字段或间接映射去猜目标页面；应尽量由后端返回明确的目标类型或目标路由，避免“看起来像对、实际跳错页面”。
- 如果用户说“打开”“进入”某条业务数据，先确认这是“查看”还是“修改”；不能默认把“打开运单”理解成“进入修改页”，报表查看和编辑入口是两个不同动作。
- 部署脚本的 Node.js 路径必须是目标级配置，并以固定安装目录为准；环境发生迁移后要移除过时的 NVM 假设，不能在远端隐式加载 NVM。
- 部署脚本判断系统服务时必须检查实际运行状态（如 `systemctl is-active`），不能只因为服务单元存在就跳过启动；启动失败应阻止后端重启并给出明确错误。
- 非交互 SSH 中，SSH 登录认证不会自动通过给 `sudo`；涉及服务管理或 Nginx 配置的远端脚本必须显式处理 sudo 认证，并让所有特权调用使用同一机制。
- MongoDB 配置也必须是目标级策略：不能因为默认 systemd 服务正在运行就认定应用数据库可用；部署前需确认该目标实际使用的配置文件与监听端口。
- 当目标服务器已有约定的项目启动脚本时，部署脚本应调用它而不是内嵌等价的进程启动命令；避免绕过该服务器已有的路径、PID 和配置管理约定。
- 排查跨环境登录加密失败时，要先沿“浏览器访问协议 → 前端加密分支 → 后端解密填充”追踪；`localhost` 与 HTTP 公网地址的安全上下文不同，不能先把问题归因于数据库副本或密钥不一致。
- Node.js 全局升级 PM2 不会自动替换内存中的旧 PM2 守护进程；迁移掉 NVM 后，要同步守护进程并重建保存的进程清单。前端这类全局 CLI 必须在 PM2 中记录目标 Node 目录下的绝对可执行路径，且部署后要校验进程已 online，不能只看 `pm2 start` 的命令输出。
- 对需要 `sudo` 的开机服务配置，不能以 `|| true` 静默吞掉失败；应复用非交互部署的认证函数并把目标 Node 的 `PATH` 传给 systemd 生成命令，否则移除 NVM 后重启会失去进程守护。
