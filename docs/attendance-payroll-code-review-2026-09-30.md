## 初次审核确定问题（修复状态见上表）

P1：影响身份安全、薪资金额或月结数据正确性，应优先修复。P2：特定操作或时序下功能错误，应在正式验收前处理。P3：较低优先级的边界体验问题。

### 1. P1：没有工号的普通员工可被管理员重置密码，进而冒用身份读取工资

位置：`utils/user-security.js:7`；调用点 `controllers/api/user.js:633`，另见通用修改/删除及旧版用户管理入口；本人工资读取 `controllers/api/payroll.js:659`。

当前员工身份是 `_id + tenantId`，工号是可选属性。`hasProtectedIdentity` 却只保护有工号、有考勤/工资角色、主账号或 admin 的账号。普通员工没有这些字段时返回 false，即使这个 userId 已有工资条和申请记录。

真实控制器的内存桩复现：

```text
linkedEmployee=true
protectedIdentity=false
管理员重置密码：HTTP 200，ok=true
以该员工身份读取本人工资，mustChangePassword=true：HTTP 200，返回1条
```

重置后的已知密码让管理员可以进入目标账号；本人工资接口也不要求先改密。管理员本来无法直接读全员工资，却可以通过接管普通员工账号读取该员工工资。同一判据也允许修改登录手机号或删除有历史关联的普通员工，产生身份恢复绕过和历史引用孤儿风险。仅按职位获得工资读取权、没有显式角色的领导账号也没有被此函数充分涵盖。

建议：账号保护与当前稳定员工身份、敏感权限和历史关联统一判定，不再依赖选填工号。保留正常身份核验恢复路径，删除有关联记录的员工使用停用。测试覆盖“无工号、无角色、已有本人已发布工资”这一组合，不能只覆盖有工号员工。

### 2. P1：修改总经理职位必然用旧 CAS 版本同步角色，留下半完成身份

位置：`controllers/api/user.js:367`、`:375`；同步写入 `:83`，旧持有人收回 `:54`。

通用用户修改先在数据库递增 `securityIdentityVersion`，随后继续用未同步版本的 `user` 调用 `syncGeneralManagerIdentity`。第二次 `identityVersionFilter(user)` 仍使用第一次修改前的版本，正常数据库会返回 `modifiedCount=0`。

设新总经理时，函数在失败前还已经收回旧总经理的考勤/工资角色和唯一标记，没有整体回滚。取消总经理职位时，同样可能只改职位却保留旧角色。

忠实模拟数据库版本的复现：

```text
修改资料：expectedVersion=3，databaseVersion=3，成功；数据库变4
收回旧总经理角色：成功
同步新总经理：expectedVersion=3，databaseVersion=4，失败
返回 ok=false；职位已经保存，角色和唯一标记没有完成
```

工资读取还直接识别 `title=gm`，因此不能把结果概括为“没人能查看工资”：更准确地说，职位、工资权限、考勤审批角色和唯一标记出现分裂，旧人和新人都可能保留 `gm` 职位而考勤角色已空。页面重试相同职位时，职位未变化也可能跳过同步，不能自动恢复。

建议：把职位与身份同步收敛为一个受角色锁保护的业务操作；正确使用更新后的 CAS 版本，并检查旧持有人写入结果。兼容独立 MongoDB 时采用有明确补偿的状态转换，失败不能只留下部分成功。还应统一清理旧职位。现有测试用无条件 `modifiedCount:1` 掩盖了这一问题。

### 3. P1：工资底稿没有传入公司缴费方案，社保公积金与薪资设置不一致

位置：`controllers/api/payroll.js:322`，漏传点 `:335`、`:338`；正确传参的标准页对照 `:426`。

`attachStandardAndAttendance(rows, tenantId, month, scheme)` 已收到公司方案，但调用 `serializeStandard` 和 `standardDraft` 时没有传 `scheme`。计算函数于是回落到默认方案，而薪资设置页使用公司实际方案。

同一员工、同一缴费基数 5000 元、公司已配置养老单位比例 16% 和公积金 5% 的控制器复现：

| 返回来源 | 单位社保 | 单位公积金 |
| --- | ---: | ---: |
| 薪资标准页 | 1425 元 | 250 元 |
| 工资管理标准及底稿 | 1675 元 | 600 元 |

个人公积金也会多带出 350 元。财务采用底稿保存时，这些错误金额会成为录入项，服务端重新计算合计无法修正错误的录入项。

建议：完整传递公司方案，并对标准页、工资底稿和录入表单建立同一公司非默认配置下的金额一致性断言。

### 4. P1：自动实到的明细展示与统计、结账快照不一致

位置：`front_end/src/pages/attendance/ledger/index.vue:113`；`controllers/api/attendance-ledger.js:268`、`:291`、`:305`、`:563`。

明细页面对非人工行使用实时 `suggestedActualMinutes` 作为“生效值”。后端统计及结账仍使用库中的 `actualMinutes`。导入、申请或日历变化后，两个数可以不同；前端脏数据判断又以当前建议值作基准，用户不会收到待保存提示。

控制器复现：

```text
原已确认 auto 实到：10560分钟（176小时）
导入无打卡1次后：建议10080分钟（168小时）
明细展示168小时；接口合计仍176小时
结账成功；closedSnapshot 实到和合计仍176小时
```

这是同一次结账中实际数值不一致，直接影响月报、历史快照及供工资管理核对的实到数据。

建议：明确区分“已确认实到”和“当前建议”。若 auto 表示随规则更新，则后端所有读取、统计及快照必须使用同一生效值；若变化后必须再次确认，则明细保留已确认值、显示新建议并阻止未复核结账。无论选择哪种当前产品规则，都应统一到同一计算入口。

### 5. P2：导入考勤次数不推进整月版本，旧页面仍能保存和结账

位置：`controllers/api/attendance-ledger.js:491`、`:495`；版本检查 `:375`、`:556`。

导入只增加 `row.version`，保存行和结账真正核对的却是 `ledger.version`。月份锁可以避免操作同时写入，不能识别导入已完成后提交的旧页面请求。

复现：导入前 `ledger.version=5`；导入成功后行版本从1变2，整月仍5；使用导入前的 `version=5` 结账返回200。普通行保存也可通过同样的版本检查，用旧确认值覆盖最新业务上下文。

建议：有成功写入的批次只推进一次整月版本，并在导入响应返回版本。行版本若不作为 API 冲突依据，应明确其用途或简化，避免两套版本看起来都有保护、实际只有一套生效。

### 6. P2：修改日历后，采用系统建议值被错误标记为人工值

位置：`controllers/api/attendance-ledger.js:250`、`:346`、`:383`、`:386`。

读台账会用当前日历重新计算 `expectedMinutes`，保存 auto 行时的 `actualSuggestionFor` 却合并库里的旧应出勤分钟。用户提交的当前建议值与后端旧上下文计算值不相等，服务端将来源改成 manual。

复现：开启周六上午后，读出的应出勤是11100分钟，库中仍10560分钟；当前建议10620分钟，以 `source=auto` 保存返回200，实际保存为manual。后续导入或日历调整不会再按自动口径更新这一行。

建议：读取、保存校验和结账共享当前月份计算上下文；核对 auto 来源前刷新应出勤值。测试覆盖“已存在行 → 改日历 → 采用新建议”。

### 7. P2：切换申请类型或分页时，旧响应可覆盖新列表

位置：`front_end/src/pages/attendance/components/RequestList.vue:253`，切类型监听 `:641`。

页面复用同一组件实例，`load()` 没有请求代次校验或取消。先请求请假，再切加班；如果加班先返回、请假后返回，旧请求仍写入 `rows/total/loading`。旧请求失败也会清空新请求已成功加载的数据。

对实际 `load()` 源码转译并注入可控异步响应的复现：

```text
新响应先到：页面类型 overtime，列表 overtime，total=1
旧响应后到：页面类型仍 overtime，列表变 leave，total=7
```

建议：复用工资管理页 `loadStatements()` 已有的 requestId 方案，并让成功、错误及 finally 都检查请求代次。审批角标同样应随当前类型刷新并防止旧响应覆盖。

### 8. P2：撤回后更正工资没有带回旧金额，只能重新按标准填写

位置：`controllers/api/payroll.js:174`、`:193`、`:619`；`front_end/src/pages/attendance/payroll/statements.vue:147`、`:333`、`:691`。

发布会删除 draft。界面要求已发布工资“先撤回再更正”，且已发布行隐藏编辑入口；撤回只清空有效版本指针，不生成修订草稿。随后接口的 `components/totals/publishedComponents` 均为空，历史版本响应只有版号、人员和时间，没有旧金额。

编辑表单只取 `row.components`，缺失时取当前薪资标准。因此原绩效、补贴、考勤扣款等不能作为修订底稿恢复，固定项也可能变成新标准，而不是原发布金额。用户原本只想修改一项，却必须重建整份工资，容易漏项。旧快照仍在数据库，**这不是永久删除历史数据**，而是当前更正流程无法读取和延续它。

建议：撤回时基于指定旧版创建修订草稿，或者提供授权读取旧版金额并复制为草稿的入口。保持员工仅看到有效已发布版本。测试覆盖“发布带绩效/扣款 → 撤回 → 编辑仅修改一项 → 其余项保留”。

### 9. P2：普通员工可以被指定代理审批，却没有常规审批入口和本人审核历史权限

位置：`front_end/src/pages/attendance/settings.vue:684`；`controllers/api/attendance.js:544`、`:729`、`:634`；`front_end/src/components/app-sidebar/data/sidebar-data.ts:40`；`RequestList.vue:68`。

代理候选人可以是没有考勤角色的普通在职员工，后端也会将总经理申请分配给此人。待审批菜单和页面判据却只认主账号、admin和考勤角色；审核历史接口也按这些角色拦截。

结果是该员工可以通过通知打开待办并处理，但没有常规侧栏入口，处理后读取自己的审核记录得到403。直接指定没有考勤角色的直属经理也有同类错配。这不是“完全不能审批”，而是实际审批身份没有贯通导航和本人历史授权。

建议：本人待办和审核历史以实际分配/审批记录授权；菜单使用明确的审批能力标记或待办身份。不要为补入口顺带授予团队或公司数据读取权限。

### 10. P2：薪资标准的刷新会静默丢弃未保存编辑

位置：`front_end/src/pages/attendance/components/PayrollStandardSettings.vue:189`、`:361`。

刷新按钮只在loading时禁用，加载成功直接清空 `editingId` 和 `drafts`。编辑基本工资等字段后点刷新，用户输入消失，没有保存、放弃或取消的提示。保存缴费方案后调用同一load也有清除正在编辑员工草稿的风险。

建议：刷新和会触发重载的入口复用同页脏数据守卫，明确保存/放弃选择，或者在有脏编辑时禁用刷新。与已经有保护的员工资料、财务授权、台账保持一致。

### 11. P3：工资批量发布/导入没有在前端处理500行上限

位置：`front_end/src/pages/attendance/components/PayrollPublishDialog.vue:53`；`PayrollImportDialog.vue:388`；后端 `controllers/api/payroll.js:770`、`:837`。

批量发布默认全选，直接提交所有员工；真实submit函数桩验证会发出501个ID，而后端整批返回400。工资导入同样原样提交全部合法预览行，未在前端限制或分批，且没有逐行取消入口，超过500行只能拆文件。

后端上限本身合理，这里没有越过保护或造成数据损坏。问题是前端已经有 `payrollBatchLimit=500` 常量，却未用于选择和提交，用户直到提交才知道整批不能处理。

建议：按现行上限明确提示并限制选中/导入行数，或以不超过500行的批次逐批提交并保留逐行结果。小公司短期不触及此边界，可以后排。

## 好的代码味道：值得保留

1. **金额模型清晰。** `utils/payroll-calculations.js` 使用整数分，校验金额范围和完整组件，由后端重算合计。前端导入不具有决定汇总金额的权力。这比接收 Excel 合计或前端计算值可靠。
2. **本人读取范围在服务端固定。** `getMyStatements` 使用登录账号ID和当前租户，不接受外部 employeeId；只暴露有效已发布版。全员读取和财务写入也有独立服务端守卫。问题1属于账号接管绕过，并不否定正常查询范围隔离的价值。
3. **版本与支付事实分开。** 工资发布追加 revisions，撤回记录 events，付款另存流水；发布不是付款。修订草稿不会替换仍有效的已发布统计。历史数据建模方向正确，更正入口需要补齐。
4. **并发防护有实际业务目标。** 唯一索引约束“员工+月份”；CAS保护编辑；请假提交锁防重复；工资发布与考勤月结/重开共享月份锁。批量发布共用单条发布逻辑，批次只核对一次月结状态。
5. **时间与历史处理有意识。** 自然月采用北京时间半开区间；请假按日保存分配，历史批准记录不因日历修改静默重算；停用账号仍可保留历史台账。
6. **未知状态没有随意冒充零。** 实到使用null，“无依据”要求原因；待审批与已批准分开统计，异常请假分配有复核标记。
7. **导入较完整。** 预览匹配员工、同名消歧、工资重复员工拦截、字段校验、逐行反馈、批量上限和服务端重算都有实现。考勤空白单元格表示不修改，避免误清已有记录。
8. **部分前端异步状态处理成熟。** 工资列表、个税基数请求已有代次校验；个税基数失败时不会直接用缺少历史的估算冒充成功。共享字段常量和工资条组件减少名称、顺序和展示漂移。
